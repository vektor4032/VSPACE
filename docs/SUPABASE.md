# VSPACE: аккаунт и синхронизация устройств

Код облачного режима готов. Для реального обмена между телефоном и компьютером нужен ваш проект Supabase, выполненная миграция и опубликованная конфигурация. Без них приложение остаётся локальным и не показывает фиктивный успешный вход.

## 1. Создать проект

1. Откройте https://supabase.com/dashboard и создайте аккаунт.
2. Нажмите **New project**, выберите организацию, имя **VSPACE** и подходящий регион. Бесплатный тариф подходит для личного использования.
3. Задайте пароль базы и сохраните его у себя. В приложении пароль базы не используется.
4. Дождитесь запуска проекта.

## 2. Создать таблицу и правила доступа

В проекте откройте **SQL Editor → New query**. Скопируйте весь файл:

[`supabase/migrations/202610220001_workspace.sql`](../supabase/migrations/202610220001_workspace.sql)

Нажмите **Run**. Миграцию можно выполнить повторно. Она создаёт:

- `public.vspace_workspaces`: один снимок пространства на пользователя;
- RLS для чтения только строки, принадлежащей `auth.uid()`;
- RPC `save_vspace_workspace`, проверяющую аккаунт и ожидаемую ревизию;
- запрет прямой записи из браузера в таблицу и запрет доступа анонимам.

RPC принимает только текущего авторизованного пользователя из проверенного JWT. Передать ID другого пользователя параметром невозможно. `service_role` в браузере не используется.

## 3. Настроить вход по почте

В **Authentication → Sign In / Providers → Email** включите вход по email/password. Рекомендуется оставить подтверждение почты включённым.

В **Authentication → URL Configuration** задайте:

- **Site URL**: `https://vektor4032.github.io/VSPACE/`
- **Redirect URLs**: `https://vektor4032.github.io/VSPACE/`

Для локальной разработки при необходимости добавьте `http://localhost:5173/` и `http://127.0.0.1:5173/`. Приложение поддерживает регистрацию, вход, выход на текущем устройстве и восстановление пароля по письму. Доставка писем зависит от настроек и лимитов почтового сервиса Supabase; собственный SMTP можно настроить отдельно.

## 4. Подключить публичные параметры

Найдите **Project URL** (Connect / Settings → Data API) и **Publishable key** (Settings → API Keys). Для старых проектов подходит публичный `anon` key.

Заполните `public/cloud-config.json`:

```json
{
  "url": "https://YOUR_PROJECT.supabase.co",
  "publishableKey": "sb_publishable_REPLACE_WITH_REAL_PUBLIC_KEY"
}
```

Это публичные параметры клиентского приложения; доступ к данным защищён сессией пользователя и RLS. Не указывайте `service_role`, `sb_secret_...`, пароль базы или Supabase Management API token. Приложение отклоняет secret/service-role ключи.

Вместо JSON можно задать переменные при сборке:

```text
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Параметры `VITE_*` включаются в публичный JavaScript. `.env.local` исключён из Git. Пример: [`.env.example`](../.env.example).

`cloud-config.json` загружается без HTTP-кеша и исключён из precache PWA. Успешно прочитанные публичные параметры кешируются на устройстве для офлайн-запуска.

## 5. Опубликовать обновлённый сайт

После конфигурации соберите под путь GitHub Pages:

```powershell
$env:VSPACE_BASE_PATH = "/VSPACE/"
npm ci
npm run build
```

Ветка `gh-pages` должна содержать результат `dist/` в корне и файл `.nojekyll`. Исходники хранятся в `main`. Само изменение исходников не обновляет опубликованную ветку автоматически.

Если проект настраивается в этой беседе, пришлите только **Project URL** и **публичный Publishable/anon key**, подтвердите выполнение SQL — и можно опубликовать сборку с вашим подключением. Управление Supabase из этой среды не подключено: миграция не выполняется в вашем проекте автоматически.

## 6. Пользоваться с разных устройств

1. На компьютере откройте VSPACE → **Настройки → Регистрация**.
2. Подтвердите почту по письму, затем войдите.
3. Если до этого уже были записи без аккаунта, нажмите **Перенести локальные записи**. Приложение запросит подтверждение замены данных аккаунта; локальный оригинал останется на устройстве. При необходимости сначала экспортируйте JSON.
4. На телефоне откройте **тот же сайт** и войдите **с той же почтой**.
5. Создайте задачу и дождитесь **«Синхронизировано»**. На другом устройстве она появится при возвращении в приложение, максимум примерно через 15 секунд при открытом экране, или после кнопки **Синхронизировать**.

Облачная синхронизация переносит задачи, привычки и их историю, проекты и этапы, меню, избранные рецепты, самочувствие, профиль и настройки. Готовая библиотека рецептов поставляется в самом приложении.

## Офлайн, конфликты и приватность

- Сначала изменения записываются в IndexedDB устройства. Без интернета они остаются там, а не считаются отправленными в облако.
- Состояния локальной записи и облачной синхронизации показываются отдельно. Перед закрытием дождитесь завершения локальной записи.
- На следующем подключении, при возврате на экран и каждые 15 секунд приложение проверяет сервер.
- Разные задачи, поля и даты привычек объединяются трёхсторонним сравнением с последним общим снимком. Удаление записи передаётся другим устройствам.
- Если одно поле изменено по-разному (или удаление столкнулось с редактированием), автозапись останавливается. Выберите **Оставить мои правки** либо **Взять правки из облака**. Выбор применяется к конфликтующим полям; независимые изменения сохраняются. Можно сначала экспортировать JSON.
- Гостевые данные и кеш каждого аккаунта изолированы в разных базах IndexedDB. Вход не загружает гостевые записи автоматически. Выход возвращает к гостевому пространству.
- Кеш аккаунта и сессия хранятся в браузере; отдельного шифрования паролем приложения нет. На общем устройстве после выхода удалите данные сайта. Не удаляйте их до отправки всех нужных изменений в облако или экспорта.
- Выход на одном устройстве не завершает сессии на других. Удаление данных в настройках очищает пространство и синхронизирует это изменение; оно не удаляет аккаунт Supabase.
- Размер одного снимка ограничен 5 МБ. При превышении лимита локальная копия сохраняется и показывается ошибка отправки.

## Проверки реализации

`npm test` проверяет слияние, удаления, конфликты, гонки ревизий, офлайн-восстановление и локальные транзакции. Отдельный тест выполняет SQL-миграцию в PostgreSQL (PGlite) и проверяет RLS, права и CAS. `npm run test:e2e` использует два изолированных браузерных профиля с тестовым Supabase HTTP API для проверки входа, переноса данных, офлайн-синхронизации, смены аккаунта и выбора версии.

Это проверки кода и локальной модели сервера. Они не заменяют запуск миграции и проверку регистрации/доставки писем/двух реальных устройств в вашем Supabase-проекте. После подключения обязательно проверьте эти действия на опубликованном сайте.
